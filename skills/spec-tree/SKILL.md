# Spec Tree

対象リポジトリの目的から実装までを、文で書いた1枚のツリーにして HTML へ書き出す。利用者は、任意のリポジトリについて、何が求められ、何が定められ、どこで実装されているかを、毎回同じ形で辿れる。ツリーは「目的 → 要求 → 機能 → 要件 → 仕様 → 実装」の6種類の節からなり、実装は仕様の子としてコミット固定のリンクを持つ。

同梱物は雛形・ビルド・検証・サンプルの4つである。対象リポジトリは読み取るだけで、書き込まない。

| ファイル | 役割 |
| :-- | :-- |
| `template.html` | 白いキャンバスの画面。データを埋め込む口が2つある |
| `validate.py` | データを対象リポジトリの固定したコミットに照らして検証する |
| `build.py` | 検証を通したデータを雛形へ埋め込み、1枚の HTML に書き出す |
| `sample/` | 小さなリポジトリとデータの例。`sample/run.sh` で検証と書き出しが通る |

## Workflow

次の手順を順に行う。データは JSON 1つで、`meta` と `nodes` からなる。形は `sample/tree.json` に従う。

### Read

対象リポジトリを読み、目的・利用者・ふるまいの根拠になるドキュメントとコードを集める。見るのは、README・仕様書・設計書・設定・コード・テストである。引用の根拠は、固定したコミットのファイルから取る。作業ツリーの未コミットの内容は根拠にしない。

`meta` に次の値を置く。

- `title`：ページの題。
- `repo`：`owner/name` の形のリポジトリ名。リンクの組み立てに使う。
- `commit`・`sha`：固定するコミット。`sha` は `commit` を解決した完全なハッシュと一致させる。
- `confirmedFiles`：利用者が仕様として確定させたと言えるファイルの一覧。
- `status`：検証の状態の説明。`platform`・`manual`・`none` の3つに `label` と `desc` を付ける。

### Group

集めた内容を、親から子へ次の順に整理する。子は親の下位の種類だけを持てる。仕様の子は実装だけである。

| 種類 | 内容 |
| :-- | :-- |
| 目的 | リポジトリが何のためにあるか。根はただ1つで、`p` は `null` |
| 要求 | 利用者が達成したいこと |
| 機能 | 要求を満たすために提供するまとまり |
| 要件 | 機能が満たすべき個別の条件 |
| 仕様 | 要件を満たす具体的なふるまい。検証の状態 `st` を持つ |
| 実装 | 仕様を実現するコードや設定。ファイルと行範囲で示す |

節の `id` は重複させず、`p` に親の `id` を書く。子の無い要求・機能・要件・仕様は作らない。

### Write

目的・要求・機能・要件・仕様の `n` は、主語と述語をそろえた1文にし、句点（`。`）で終える。1つの節に1つの事柄だけを書く。要求は「利用者は、〜ことができる。」、機能・要件・仕様は「<対象>は、〜する。」の形にする。仕様の主語は、ふるまいを担うファイルや部品にする。

### Provenance

目的・要求・機能・要件・仕様の出所を `pv` で区分する。

| 区分 | 意味 | `refs` |
| :-- | :-- | :-- |
| 確定 | `confirmedFiles` のファイルが、そのとおりに定めている | 必須。1つ以上が `confirmedFiles` のファイル |
| 記載 | リポジトリのドキュメントやコードに書いてある | 必須 |
| 推定 | 書き手が読み取って補った | 置かない |

`refs` は `{"k": 種別, "f": ファイル, "l": 行, "q": 引用}` の並びである。`l` は `N` か `N-M` で、`q` はその行の原文からそのまま取る。離れた箇所は ` / ` か `…` でつなぐ。

### Status

仕様の `st` に、そのふるまいが守られていることの確かめ方を `meta.status` のキーで置く。自動テストやツールが守らせるなら `platform`、手順書の規約だけなら `manual`、どちらも無ければ `none` とする。

確かめ方が足りない箇所や、読み取れなかった点は、仕様の `gaps` に `{"ty": 種類, "tx": 内容, "pv": "確認" または "推定"}` で残す。根拠のファイルを示すときは `refs` に `"ファイル:行"` の文字列を置く。

### Link

実装の節は `{"k": 種別, "f": ファイル, "l": 行, "q": 引用}` を持ち、親は必ず仕様である。ビルドが `meta.repo` と `meta.sha` から、その行を指すコミット固定のリンクを組み立てる。Markdown ファイルは行表示のために `?plain=1` が付く。

実装が無い仕様には、ただ1つの子として `{"n": "記載のみで、実装は無い。"}` の節を置く。リポジトリの外にある実装は、`f` を `（外部）` で始め、`url` に `https://` で始まる行き先を置く。

### Validate

次のコマンドでデータを検証する。`TREE_JSON` はデータ、`REPO_DIR` は対象リポジトリである。

```shell
python3 validate.py TREE_JSON REPO_DIR
```

次のような誤りは明示的なエラーとして止まる。エラーが無くなるまでデータを直す。

- 実装節の親が仕様でない。
- 文が句点で終わらない。
- 行範囲がファイルの長さを超える。
- 引用がその行に無い。

検証は、書式・参照・原文の一致を機械で確かめる。文が原文の意味と合うかは確かめられない。

### Compare

検証を通した後に、作成者自身が文と原文を突き合わせる。各節について、`n` の文が `refs` や `q` の原文と同じ意味かを読んで確かめる。原文に無い断定、原文より広い範囲の言い切り、主語のすり替えがあれば、文を直す。直しても原文と合わなければ、出所を `推定` に改める。

### Export

次のコマンドで HTML を書き出す。`OUT_HTML` の場所は利用者の作業場所に置き、対象リポジトリには書かない。ビルドは検証を先に行い、通らなければ書き出さない。公開はしない。

```shell
python3 build.py TREE_JSON REPO_DIR OUT_HTML
```

### Check

書き出した HTML を `/ego-browser` で開き、次を確かめる。

- 白いキャンバスに、根の目的と要求が表示される。
- ドラッグで移動し、拡大縮小できる。
- 節を開閉できる。
- 仕様の課題を表示できる。
- 実装のリンクが、固定したコミットの該当行を開く。

## Sample

`sample/run.sh` は、一時フォルダに小さな git リポジトリを作り、`sample/tree.json` の `__SHA__` をそのコミットへ置き換えて、検証と書き出しを通す。データの書き方に迷ったら、このサンプルを手本にする。

```shell
sh sample/run.sh
```
