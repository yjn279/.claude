# Offload

直近のセッション履歴を読み、作業をいまより安い担い手へ移す提案を作る。担い手は、人、エージェント、高コスパモデル、スクリプトの順に安く、確かになる。人からエージェントへ移せば人の時間が空き、上位モデルから下位モデルへ移せば費用が下がり、モデルからスクリプトへ移せば費用がほぼ消えて結果が毎回同じになる。

提案は、移す価値があるものに絞る。移すと品質が落ちるもの、頻度が低く元が取れないもの、失敗の損失が大きいものは、そのまま残すと判定して理由を添える。最善の自動化は作らずに済ませることでもあるため、既存の Skill・フック・ルールを直せば済む場合は新設より改修を選ぶ。

このスキルは提案で終わる。利用者が選んだ提案だけを、承認を得てから実装する。

## Collect

同梱の `digest.py` で、履歴を1枚の要約にする。読み取るだけで、何も書き込まない。

```shell
python3 <this skill's directory>/digest.py --days 7
```

対象は `~/.claude/projects/` の会話記録と、`~/.claude/` の設定である。件数が少なく傾向が見えなければ `--days 14` や `--days 30` に広げる。要約の各表が示すものは次のとおりである。

| 表 | 示すもの |
| :-- | :-- |
| Projects | プロジェクトごとの会話の数と、出力トークン |
| Tokens by model | モデルごと、本体・サブエージェント・advisor ごとのトークン。キャッシュの書き込みは保持の長さ（5分・1時間）で分ける |
| Subagents | サブエージェントの種類とモデル、使った量、任された作業の例 |
| One-off requests | 他の会話と重ならない最初の依頼。人が頼んでいる仕事にあたる |
| Routine session groups | 同じ最初の依頼で繰り返し起きる会話。定期実行やボットにあたる。共通の雛形のうち会話ごとに違う部分を Variants に分けて示し、これが実際の作業の種類にあたる |
| Repeated follow-ups | 2つ以上の会話で繰り返し送られた承認・訂正・催促。依頼の文全体が一致したものだけを数える |
| Slash commands and skills | 呼ばれたコマンドと Skill |
| Tools / Repeated shell commands / Repeated tool sequences | 繰り返す道具の使い方と、失敗の数 |
| Injected text | フックや通知が会話へ差し込んだ文。何度も出るフックの指摘は、エージェントが同じ規則を外し続けている印である |
| Existing configuration | すでにある Skill・エージェント・ルール・定期実行・フック・モデルの設定と、プロジェクトごとの設定 |

会話の種類のうち `relayed` は、Orca や `claude -p` などの SDK から届いた依頼で、記録の上では人か自動かを区別できない。他の会話と最初の依頼が重ならない `relayed` は人の依頼である見込みが高く、重なるものは自動の見込みが高い。

要約に映らないものが2つある。1つは、フックやスクリプトが会話の記録を残さずに呼ぶモデル（ `claude -p --no-session-persistence` など）で、使った量は測れない。もう1つは、Claude の外の仕組みで定期に動くもの（ `launchd` ・ `cron` ・ Orca などのツールの自動実行）である。どちらも、該当するフックやスクリプト、ツールの一覧を直接読んで補う。

## Inspect

要約は手がかりであり、証拠ではない。提案の候補にしたものは、元の会話を開いて中身を確かめる。依頼の文や繰り返すコマンドで `~/.claude/projects/` を検索して会話を見つけ、`--session` で1つの会話を縮めて読む。サブエージェントの記録も、末尾に並ぶパスを渡せば同じ形で読める。

```shell
python3 <this skill's directory>/digest.py --session <会話の id の先頭、または記録のパス>
```

読むのは、実際の手順、エージェントが迷った箇所、やり直した箇所、人が手を入れた箇所である。

同じ課題を、過去の会話がすでに調べて提案していないかも検索する。返事のないまま残った提案があれば、新しい発見としてではなく、既出の提案として示す。

候補が既存の設定に触れるときは、その Skill・フック・エージェント・定期実行の定義を読み、重なりを確かめる。同じ目的のものがあれば、新設ではなくその改修として提案する。

費用は、要約のトークンに `claude-api` Skill で確かめた現在の単価を掛けて求め、覚えている値は使わない。キャッシュの書き込みは保持の長さで単価が違う。利用者がサブスクリプションで使っているなら、ドルの換算は目安にとどめ、使用量の上限の減り方として伝える。

## Judge

候補ごとに、どの段を移すかを決め、筋の良さを判定する。次の3段で考える。

| 段 | 兆候 | 筋が良い | 筋が悪い |
| :-- | :-- | :-- | :-- |
| 人 → エージェント | 人が繰り返す依頼、承認、訂正、催促。人が手で行う定型の確認や操作 | 判断の基準を言葉にできる。結果を確かめられる。失敗しても戻せる | 公開・送金・人への連絡のように本人の責任を伴う。好みや文脈に強く依存する。頻度が低い |
| 上位モデル → 下位モデル | 上位モデルで動く、読むだけの調査、要約、整形、分類、決まった観点での検証。出力の形が決まった定型の会話 | 入出力の形と手順が決まっている。誤りを機械的に見つけられる | 曖昧な要求の解釈、設計の判断、長い自律作業。やり直しの回数が増えて節約が消える |
| モデル → スクリプト | 同じシェルコマンドや道具の並びの繰り返し。道具の使い方が毎回同じ定型の会話 | 同じ入力に同じ答えを返せばよい。分岐が少なく、手順が安定している | 相手の画面や API がよく変わる。例外の扱いに判断が要る。文章の生成そのものが目的である |

筋の良さは、次の5点で判定する。どれかが大きく欠ければ、移さずに残す。

- 頻度：週に何回起きるか。少なければ、仕組みを作る手間の元が取れない。
- 確定性：同じ入力に同じ結果を求めてよいか。高いほど下の段へ移せる。
- 検証：移した後の出来を、何と比べてどう確かめるか。確かめられないものは移さない。
- 失敗の損失：移した先が誤ったとき、何が壊れ、誰がいつ気づくか。
- 効果：空く人の手間、減るトークン、減る待ち時間の見込み。

## Package

移すと決めた候補を、どの器に入れるかを決める。器は、いつ働くか、誰が起動するかで選ぶ。

| 器 | 向く作業 | 置き場所と要点 |
| :-- | :-- | :-- |
| ルール | 毎回守ってほしい方針。何度も繰り返す訂正 | `CLAUDE.md` 、または `.claude/rules/*.md` 。frontmatter の `paths` で、特定のファイルを扱うときだけ読ませられる |
| Skill | 特定の作業で読む手順や知識。同梱するスクリプト | `.claude/skills/<name>/SKILL.md` 。frontmatter の `model` と `context: fork` で、下位モデルの別の文脈で動かせる |
| カスタムエージェント | 独立した文脈で任せる役割。モデルや使える道具を固定したい作業。下位モデルへ移す受け皿 | `.claude/agents/<name>.md` 。frontmatter の `model` ・ `tools` ・ `effort` で担い手を固定する |
| フック | 毎回必ず行う検査・整形・記録。ルールを守らせる仕組み | `settings.json` の `hooks` 。判断が要らなければ `command` 型でスクリプトを動かし、判断が要れば `prompt` 型で `model` を指定する |
| ルーティーン | 時刻や間隔で起動する作業 | 手元のファイルが要ればデスクトップアプリの定期タスク（アプリを開き、機械が起きている間だけ動く）。機械を止めても動かすならクラウドの定期タスク（ `/schedule` 、間隔は1時間以上）。モデルが要らなければ `launchd` や `cron` でスクリプトを動かす |
| 既存の仕組みの改修 | 利用者のリポジトリにある自動化のコードやスクリプトの中で、モデルの指定や手順を変えれば済む作業 | そのリポジトリ。変更は、そのリポジトリの運用に従う |

ルールで足りるものに Skill やフックを作らない。ルールを書いても同じ訂正が続くなら、フックで機械的に守らせる。`~/.claude/` に置けばすべてのプロジェクトに、プロジェクトの `.claude/` に置けばそのプロジェクトだけに効く。器の細かな書き方は、作る段で公式の文書と関連する Skill（ `skill-creator` ・ `update-config` ・ `schedule` など）で確かめる。

## Report

提案を、効果と確かさが大きく、手間が小さい順に並べて報告する。最初に一覧の表を置き、続けて提案ごとの中身を書く。

| 順位 | 提案 | 段 | 器 | 判定 | 見込み |
| :-- | :-- | :-- | :-- | :-- | :-- |

判定は「推す」「様子見」「見送り」のいずれかとする。推すものと様子見のものには、提案ごとに次を書く。様子見のものには、何が分かれば推すに変わるかも添える。

- 根拠：要約の数字と、確かめた会話（日付・プロジェクト・依頼の要旨）。
- 移した後の姿：作る、または直すファイルと、その中身の要点。
- 確かめ方：移す前と後を、何で比べるか。
- 失敗したときの損失：壊れるものと、気づく手段。

見送りと判定した候補も、表に理由を一行ずつ添えて残す。同じ候補を次回また検討せずに済むためである。確かめられなかった事実は、最後にまとめて挙げる。

最後に、推す提案のうちどれを実装するかを利用者に尋ねる。承認されたものだけを実装し、実装は器ごとの Skill と、対象リポジトリの運用（ `git-flow` など）に従う。
